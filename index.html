Haimcore

Next.js AI workspace with Amirani assistant

2025 – 2026 · Lead AI software engineer · freelance

Operational AI-assisted workspace where users dump content into drafts, folders and notes — Amirani, the in-product assistant, summarises across it and answers questions in context. I owned the product across three releases and the deploy / rollback pipeline that keeps prod survivable.

  • Three production releases shipped — v3 multilingual, v3.1 stability, v4 UX overhaul — with a tagged pre-deploy snapshot & rollback path. Zero downtime rollbacks.
  • Amirani wired direct to Anthropic’s SDK with a lazy resolveAnthropicKey() that reads .env.local when the shell shadows it, plus a forced base URL.

  • Multilingual across 47 languages with aliases & fuzzy lookup in the AI Actions menu — non-English keyboards still find the right option.

Relief Guru

Telegram-driven AI avatar video pipeline

2025 – 2026 · AI automation engineer · freelance

A pharmacy-content business needed to publish AI avatar videos across YouTube, LinkedIn and Instagram, controlled from Telegram so non-developers can run it. I built that pipeline as seven coordinated n8n workflows — V1 was one giant graph and impossible to debug.

  • Seven single-purpose workflows — WF1A intake router, WF1B script generator, WF2A HeyGen video, approval bridge, WF2B posting core, WF3 tracker, layout callback. Every failure traceable to a single workflow ID.
  • Defensive HeyGen payload parser probes every reasonable JSON path for the script + avatar/voice IDs and hard-fails locally with the keys it saw — way better than HeyGen’s opaque “Bad request” 90 seconds later.
  • Idempotency guard via n8n static workflow data: run_id → timestamp for 30 minutes, prevents Telegram retries from spawning duplicate HeyGen renders.
  • Sticky Telegram message UX — the workflow edits one message in place across the lifecycle of a task rather than spamming the chat. Looks like a progress bar.

Stack — what each piece does

n8n (V4)
seven coordinated workflows, single-purpose webhooks per step
Telegram Bot API
operator UI; slash commands; sticky-message progress
OpenAI embeddings
text-embedding-3-small on every brief for template retrieval
Pinecone (vector)
template store + tracker memory (“what did we say last time?”)
HeyGen v2 API
avatar video generation with 40×30s poll loop
Google & LinkedIn APIs
native posting to YouTube / Drive / LinkedIn / Instagram
The bit that bit me

Telegram’s Edit Sticky HTTP node returns its own {ok, result, …} object, which becomes $json for the next code node. Lost ~30 minutes before realising “script missing” was actually the upstream context being shadowed. Now Clean Script explicitly reaches back to the parse + idempotency nodes by name.

  • JALARAM SUPER-AI Copilot — GPT-4o with tool calling against the Postgres schema. Tools: search_patients (by name or PAT-1-2026-format ID) and get_patient_context (full clinical bundle). Per-doctor chat sessions, auto-titled by the model.

  • Gynae / Obstetrics-shaped schema — GPAL counts (gravida, para, abortions, living children), pregnancy module with trimester + risk, menstrual cycle tracker with ovulation / fertile-window prediction, operation records with anaesthesia & complications.
  • Four portals, one backend — Patient view, Doctor dashboard (consultation form + Copilot), Staff Ops Center (live counts + call attempts), Admin (users, audit log, metrics).

The bit that bit me

Role logic in the controllers is the easy thing to get wrong. When STAFF or ADMIN creates a prescription on behalf of a doctor, the supervising doctorId has to come from the request body, not the caller’s JWT. Saved me a class of “prescription signed by reception” bugs.

SATALITE Delhi

Strict EGMS-L3 road-subsidence pilot — Najafgarh Road, SW Delhi

April – May 2026 · InSAR / remote-sensing engineer · freelance

Strict EGMS-L3 equivalent road-subsidence map — vertical and east-west deformation per pixel, ITRF14 absolute frame, ERA5 atmospheric correction, two-track decomposition. End to end on a local Linux workstation with open-source tools (no AWS, no managed services in the science pipeline).

  • 2,656 detected PS — 2,555 retained after the strict EGMS-PSI gate (spatial coherence ≥ 0.70 in both stacks). V_U −10.3 to +4.7 mm/yr; V_E −7.8 to +8.4 mm/yr; residual RMS ~2 mm.
  • 165 SLC bursts → 476 SBAS interferograms pair-by-pair in SNAP (ESD coregistration, 35×6 multilook to ~80 m, Goldstein, externalised SNAPHU because SNAP’s internal wrapper stalled silently).
  • ITRF14 frame tie via Indian-plate Euler pole (Altamimi 2017), MIDAS-validated against LCK4 / HYDE / IISC GNSS — residuals coherent at −4 to −6 mm/yr east across a 1,700 km span (small known bias).
  • True 2D V_U + V_E decomposition per-pixel by Cramer’s rule. Per-pixel determinant ~0.95 across the AOI (anything above 0.3 is usable).

SNAP / ESA STEP
per-pair interferogram chain; XML graph driven by gpt

The bit that bit me

Three ERA5 GRIB files came back zero bytes from the CDS endpoint. tropo_pyaps3 segfaulted on one of them three days later. Error was uninformative — “Segmentation fault” with no traceback. Now I eccodes-check every GRIB after download.

SATALITE Kite Beach

L2-equivalent Sentinel-1 InSAR pilot — Visakhapatnam

April – May 2026 · InSAR engineer · freelance

First InSAR pilot for the SATALITE brief. Sentinel-1 road-subsidence monitoring at Kite Beach Road, Visakhapatnam. Descending-only by necessity — the site sits in a known Sentinel-1 ascending gap over coastal east India. The pilot that validated the pipeline before the strict-L3 Delhi run.

  • The catalog check is the real story. Exhaustive ASF API probe across every product type returned zero ascending granules for a 3-yr window at this AOI. Stating it up front in the client doc saved them time.
  • 86 SLC bursts → 244 SBAS pairs → 152 PS at temporal coherence ≥ 0.85. LOS velocity −11.7 to +8.5 mm/yr, RMSE ~5 mm (within the EGMS noise floor).
  • Pipeline scaffold reused for Delhi. The numbered script chain (01_* through 20_*) from this pilot got upgraded and reused for the strict-L3 Delhi run — that was the point of the validation pilot.
  • Most-subsiding PS at 17.7174 N, 83.3222 E — west of the road, built-up area. Flagged for client follow-up.

Stack — what each piece does

Sentinel-1 SAR
86 SLCs, descending track 19, IW1, VV polarisation
ASF HyP3
SBAS pair generation, 250 submitted, 244 retained
MintPy SBAS
time-series inversion with coherence-based network modification
Streamlit + Plotly
client-facing dashboard with velocity map + time series
Python + GeoPandas
numbered pipeline scripts (01_* through 20_*)
The bit that bit me

The demo sentinel1_burst_2026-04-19.tiff is raw SLC complex data (CInt16, complex64, no projection). It will not display in QGIS without amplitude extraction + georeferencing. A reminder that not every .tiff on an InSAR project is a raster you can open and pan.

HOW I WORK

Five principles I’ve earned the hard way.

  • Bias to shipping. I’d rather get a v0 in front of the user this week and learn what’s actually wrong than spend a month polishing the v3 of someone’s spec.
  • Defensive at the seams, light in the middle. Where my code meets a third-party API or an LLM, I hard-fail with the actual thing that broke. Inside the code I trust myself.
  • Audit logs over comments. Useful comments are about why. But what I really care about is being able to reconstruct what happened — SystemLog on hospital, run trackers on Relief Guru, audit folders per release on Haimcore.
  • Hedging is honest. If a parameter I’ve picked won’t generalise outside the AOI / customer / case I had in front of me, I say so in the report. Better than the client finding out the hard way.
  • Make the un-fun parts repeatable. Deploy scripts, smoke tests, rollback paths, idempotency guards. Everything that bit me once gets a guard rail.
