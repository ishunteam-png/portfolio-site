Case study · What I built

I built this as a Next.js application (pages router) with the API routes doubling as the back-end. The workspace is folders and drafts on the left, an editor in the middle, an Ask-About panel on the right. Specialised editors for text, URLs (with an Open-Graph fetch I had to put a small SSRF guard around), images (vision-model description), and a “Note Mode” that attaches notes to a specific folder or file.

Amirani is wired straight to Anthropic’s SDK. Two small headaches I worked around: the shell environment on the EC2 host had an empty ANTHROPIC_API_KEY= exported that was shadowing my .env.local, and a stale ANTHROPIC_BASE_URL= from an older proxy experiment. I wrote a tiny resolveAnthropicKey() in the legacy shim that reads .env.local directly as a fallback and forces the base URL to api.anthropic.com — saved me from ever debugging that one again.

A small insight route that the image describer and Ask-About panel both post into. It appends to data/memory/summary_default_<date>.md so the next Amirani call sees today’s AI-generated content as context. Closes the loop without me having to design a full memory store.

Auto-save is a 1.5 second idle trigger plus a final sync save on editor unmount. There’s an onDraftRebind subscription so when a new draft swaps from a temporary optimistic ID to its real DB id, every component holding that reference updates without re-rendering or losing focus.

Deploy story: tagged pre-deploy snapshots, source-only bundles uploaded to S3, a Postgres rollback instance kept around for the v4 cut-over as a safety net, a manual pre-rollback-backup-<date> folder before any destructive change to source.

“I’ve had to fall back to the snapshots once and it was worth the discipline.”

Case study · The bits that bit me

After the v4 file overlay, the Anthropic SDK install lost models.mjs and a couple of beta resources — the streaming endpoint then returned an unhelpful 500. Reinstalling @anthropic-ai/sdk@latest fixed it, but I now reinstall the SDK whenever I overlay a release rather than trusting the file copy.

Two legacy shims (system-health.js + a missing workspace-synthesize.js) had stale ../../../lib/X imports after their move. The build went red, the cut-over paused. After fixing them I wrote a smoke check that exercises every shim before declaring a deploy green.

Recovered a 729 MB Downloads folder from the Recycle Bin during an incident-response session. Worth saying out loud: I now stash a daily zip of haimcore/ outside the working tree, because the Bin is not a backup.

The legacy-shim pattern is worth describing because it has saved me from a class of bugs. Anything that used to live at pages/api/…/foo.js moves to lib/legacy/foo.js, behind a thin v4 wrapper that adds CSRF + session handling. Each shim is exercised by the smoke test on every deploy, so an import-path break in a forgotten file shows up before the deploy lands, not after.

Relief Guru

Telegram-driven AI avatar video pipeline

2025 – 2026 · AI automation engineer · freelance

A pharmacy-content business needed to publish AI avatar videos across YouTube, LinkedIn and Instagram, controlled from Telegram so non-developers can run it. I built that pipeline as seven coordinated n8n workflows — V1 was one giant graph and impossible to debug.

Case study · What I built

Why seven workflows. V1 was one giant n8n workflow with branching logic and “sub-functions” called by HTTP. It worked until the day it didn’t, and when it broke I couldn’t tell whether the failure was at intake, at script generation, at HeyGen, or at posting. V4 splits it into single-purpose webhooks — every step lives in its own workflow with its own logs.

WF1A — Intake Router. Telegram webhook into n8n. Admin whitelist by chat ID. Slash-command parser: /start, /help, /avatars, /voices, /templates, /new, /refresh_avatars, /refresh_voices, /status, /last, /company. Routes the request into the right downstream workflow with a stable run_id.

WF1B — Template + Script Generator. Take the brief, embed it with OpenAI text-embedding-3-small, query Pinecone against the templates namespace. Top-10 normally, top-100 if the operator gave a template hint, optional content_purpose filter. GPT writes the script against the closest template, the operator gets it back in Telegram for review.

WF2A — HeyGen Video Generation. The hairy one. Studio app posts a payload that, depending on which trigger fired, has the script under body.script, body.video_inputs[0].voice.input_text, body.text, or somewhere else. I wrote a Parse Studio Payload node that probes every reasonable path and, as a last-ditch, walks the whole payload looking for a string field with a name like script / text / input_text longer than 20 characters. If it doesn’t find one it hard-fails locally with the keys it saw.

Idempotency guard. n8n’s static workflow data stores run_id → timestamp for in-flight runs. A duplicate run_id within 30 minutes throws. Cleared lazily on every entry. Prevents Telegram retries (or the operator clicking a button twice) from spawning a second HeyGen render.

“V1 was one giant n8n workflow. Splitting it into seven single-purpose webhooks made every failure traceable to a single workflow ID.”

Case study · The full chain

Sticky messages. Rather than spamming the chat with “recording… rendering… uploading… posted”, the workflow edits a single Telegram message in place. Same message_id for the lifecycle of the task. Looks like a progress bar in the chat.

HeyGen poll loop. 30-second cadence, max 40 attempts (~20 minutes). The script-cleaning step strips zero-width characters, smart quotes, HTML tags, markdown, and stage-directions in brackets/parens/braces. Truncates at the last sentence end below the 1500-character HeyGen cap.

WF2A↔WF2B — Approval Bridge. Once HeyGen is done, the operator approves in Telegram. Approval token is signed; no spoofing.

WF2B — Posting Core (native). Google Developer Console for Drive + YouTube; LinkedIn Developer Console for the LinkedIn post; Instagram via Meta API. Each posting is its own retry-safe sub-flow.

WF3 — Tracker Engine. Every step in every run logs a row with task_id, trace_id, log_type, workflow_id, step, status, state, embed_text. The embed_text (first 500 chars of the script if available, otherwise the topic) goes back into Pinecone so the next run can retrieve “what did we say about this topic last time”.

The bits that bit me

HeyGen used to fail silently because input_text was empty — the script was nested deeper in the payload than the parser knew about. After two of these I rewrote the parser to be paranoid and label each rev in the comments. Last revision: v2026-05-03 rev2.

Telegram’s Edit Sticky HTTP node returns its own {ok, result, …} object, which becomes $json for the next code node. Lost ~30 minutes before realising “script missing” was actually the upstream context being shadowed. Now Clean Script explicitly reaches back to the parse + idempotency nodes by name if $input doesn’t have what it expects.

Four portals, one backend. PatientPortal — the patient’s view: appointments, medical records, prescriptions, lab reports, menstrual-cycle tracker. JALARAM SUPER-AI Copilot. GPT-4o with tool calling against the Postgres schema. Two tools: search_patients (by name or by PAT-1-2026-format hospital ID) and get_patient_context (the full clinical bundle for a given patient). The system prompt locks the assistant’s identity, names it explicitly, and says authorisation is handled at the login layer — the model is told not to refuse for “privacy” reasons inside the app, because the JWT has already done the role check. Doctor AI Insights. Gynae / Obstetrics-shaped data model. Case study · Production + the bits that bit me

Reports + lab uploads. Multer-S3 to AWS S3 in the ap-south-1 region, signed URLs back to the front-end. The Report table has an aiSummary field — the next iteration auto-summarises uploaded ultrasounds and lab reports back into the patient’s timeline. Lazy-init OpenAI / S3 clients so the env is read at call time and a misconfigured deploy fails loudly instead of silently using a stale key.

Production hardening. Express 5 + TypeScript + Prisma 6 + Postgres. JWT in HTTP-only cookies, bcrypt password hashing, helmet for security headers, a CORS whitelist that includes shreejalaramhospital.live and localhost for development. 20 MB JSON body limit so report uploads with embedded base64 thumbnails still parse. Request logger middleware on every route. Two date helpers because dashboards compute “today” in IST: getTodayBounds() and getTomorrowBounds() round-trip through the +5h 30 offset rather than trusting Date defaults.

Deploy. Docker + docker-compose + Nginx (TLS) + PM2 on EC2, with Prisma migrations baked into the start script. deploy_to_live.ps1 on the local side, setup_ec2.sh + start_pm2.sh on the box. Frontend served via a small serve_frontend.cjs bridge for Vite’s built output.

The bits that bit me

Role logic in the controllers is the easy thing to get wrong. When a STAFF or ADMIN creates a medical record or prescription on behalf of a doctor, the supervising doctorId has to come from the request body, not the caller’s JWT. DOCTOR-role creates pull from JWT. Wrapped that branch in the controller and added a 400 if STAFF/ADMIN forgets to send the doctor’s ID — saved me a class of “prescription signed by reception” bugs.

The OpenAI calls were originally constructed at module load. If process.env.OPENAI_API_KEY wasn’t set yet (e.g. PM2 starting before .env was fully sourced), the client was permanently broken until restart. Moved both OpenAI and S3 clients to lazy getters — getOpenAI() / getS3Client() — that re-read env at call time. Fixed by inspection, never had to debug it under load.

Cycle-irregularity alerts are noisy by default — 21/35-day thresholds are textbook but pull in too many patients on a real roster. The dashboard currently flags them but I’ve been tempted to add a per-doctor configurable band; haven’t shipped that yet because the doctors actually want to see the long tail.

Case study · What I built

The site choice itself was the first piece of work. I went into this expecting to pilot at Visakhapatnam — coastal subsidence is the obvious story for an Indian road. A 30-second ASF catalog check killed that: no ascending Sentinel-1 coverage at all. Without ASC + DSC you can’t do strict EGMS-L3 decomposition. Mumbai and Bangalore had the same gap. That left Delhi and Kolkata as the two dual-track-covered Indian metros. I picked Delhi — well-documented groundwater subsidence in southwest Delhi in the literature, inland (no coastal geoid effects to fight during atmospheric correction), and Najafgarh Road in Sector 8 Dwarka is real road infrastructure the client can point to.

Data: 165 Sentinel-1 SLCs across 3 years. ASC relative orbit 27, IW2, 88 acquisitions. DSC relative orbit 136, IW1, 77 acquisitions. ~12-day cadence (S1A only — S1B failed end-2021 and S1C didn’t come online for the Delhi pass until mid-2025). The geometric point that mattered later: ASC sits west of the AOI looking east, DSC sits east looking west — antiparallel horizontal LOS vectors with similar incidence angles, ~33°. That’s what makes the 2×2 V_U+V_E decomposition well-conditioned.

Workstation and software. 12-core / 32 GB / 2 TB SSD on Ubuntu 22.04. SNAP for the per-pair InSAR work — bumped the JVM heap from the default 8 GB to 20 GB in ~/snap/etc/snap.properties because the default crashes on coregistration of large bursts. Python 3.10 conda env with MintPy + SNAPHU + asf_search + sentineleof + rasterio + geopandas + pyproj + h5py from conda-forge; PyAPS3 from GitHub (it’s not on conda-forge). I never touch h5py manually after the one time I mixed pip and conda installs and segfaulted MintPy at load_data.

SBAS network. Each acquisition pairs with the three nearest forward neighbours, max temporal baseline 60 days. Past 60 days Delhi’s monsoon decorrelation is too severe in my experience to be worth processing. 258 ASC + 218 DSC = 476 pairs.

SNAP per pair. TOPS coregistration with ESD, interferogram formation, topo phase removal against Copernicus 30 m DEM, deburst, 35×6 multilook (~80 m pixels), Goldstein filter, SNAPHU unwrap, terrain correction to UTM 43N. I split the graph into two halves around the SNAPHU export/import — SNAP’s built-in SNAPHU wrapper stalled silently on three different pairs early in the run with no useful log entry.

ERA5 atmospheric correction. Tropospheric water vapour adds ~1–2 cm peak-to-peak LOS noise over Delhi across a year. Without correction it bleeds into the velocity as a fake annual cycle, especially for any pixel near vegetation. I batched CDS requests overnight — 01:00 UTC for descending (~06:00 local pre-dawn), 13:00 UTC for ascending (~18:00 local). About 300 GRIB files.

MintPy SBAS. Separate workspaces mintpy_asc/ and mintpy_dsc/. correct_troposphere with the ERA5 step is the slow one, ~25 minutes per stack. Residual RMS settled at ~2 mm in both stacks; EGMS noise floor is ~2–3 mm so I called this good enough.

ITRF14 tie via the Indian-plate Euler pole. MintPy gives relative velocities (reference pixel = 0). EGMS L3 wants absolute ITRF14. With no co-located GNSS at the AOI I used Altamimi et al. (2017)’s plate-motion model. Pole at φ = 50.295°N, λ = −8.155°E, Ω = 0.554°/Myr; at my AOI that’s V_E ≈ +40 and V_N ≈ +39 mm/yr, V_U = 0 by rigid-plate assumption.

Decomposition. Solved the 2×2 (V_E, V_U) system per-pixel by Cramer’s rule; the per-pixel determinant rides at ~0.95 across the AOI (anything above 0.3 is usable, 0.95 is comfortable).

Case study · The bits that bit me

Multilook calibration. First batch was 30×5 looks. A few pairs in I noticed the result over the road corridor was smeared — small-target PS getting averaged into their neighbours. Reran a subset at 35×6 (~80×84 m), visibly cleaner, locked it in. EGMS L3 is at 100 m formally; 80 m gave me a slightly finer grid without exploding compute.

SNAP JVM OOM. The pattern was always the same: a large burst pair, four gpt processes running in parallel, OS killing the JVM. After the second time I capped parallel at three concurrent pairs and the crashes stopped. Throughput dropped from ~5 pairs/hour to ~4. I lived with it.

ESD threshold on a few pairs. Default ESD coherence threshold is 0.3. A handful of pairs failed there; I dropped to 0.2 for those specific pairs and they coregistered fine. Not ideal — a lower threshold means trusting a noisier azimuth-shift estimate — but the AOI itself was high-coherence even though the broader burst had a low-coherence stretch. Acceptable for this AOI; would not generalise.

ERA5 zero-byte GRIBs. Three GRIB files came back zero bytes from the CDS endpoint and tropo_pyaps3 segfaulted on one of them three days later, when MintPy tried to read it. Error was uninformative — “Segmentation fault” with no traceback. I now eccodes-check every GRIB after download.

Mid-stack shape mismatch. Pair 20240623_20240705, a monsoon-window pair, had a slightly different raster size after deburst — probably because SNAP’s auto burst-selection caught a different sub-burst due to a slight orbit shift. Regenerated that one pair separately with explicit firstBurstIndex / lastBurstIndex matching the rest of the stack.

2024 SAFE-layout shift. ASF’s cloud-native rollout in 2024 changed the inner directory layout of the newer SLCs slightly. SNAP’s default Read node initially refused to recognise a handful of the newer scenes. A small file-pattern tweak in the SNAP graph fixed it — lost ~an hour figuring out it wasn’t a corrupt download.

“Acceptable for this AOI; would not generalise.”

The catalog check became a one-time 20_check_track_coverage.py script I now run before quoting any new InSAR site.

Burst SLC display. A side artifact — the sentinel1_burst_2026-04-19.tiff demo file is raw SLC complex data (CInt16, complex64, no map projection). It will not display as a normal radar image in QGIS without amplitude extraction + georeferencing. A reminder that not every .tiff on an InSAR project is a raster you can open and pan.

Limitations called out in the client doc (deliberate, addressable in the full project): single descending track only (no ascending → no full 3D decomposition), no ERA5 atmospheric correction applied yet (would reduce noise ~50%), local reference frame (not tied to ITRF). All four of those got upgraded for Delhi, by design.

“Stated up front — saves the client the time of asking.”
// 06 How I work FIVE PRINCIPLES · EARNED THE HARD WAY
PRINCIPLES

The five rules I’ve earned the hard way.

Patterns I keep coming back to after every project. The kind of thing that’s obvious in hindsight but expensive in real time.

  • Bias to shipping. I’d rather get a v0 in front of the user this week and learn what’s actually wrong than spend a month polishing the v3 of someone’s spec.
  • Defensive at the seams, light in the middle. Where my code meets a third-party API or an LLM, I hard-fail with the actual thing that broke. Inside the code I trust myself.
  • Audit logs over comments. Useful comments are about why. But what I really care about is being able to reconstruct what happened — SystemLog on hospital, run trackers on Relief Guru, audit folders per release on Haimcore.
  • Hedging is honest. If a parameter I’ve picked won’t generalise outside the AOI / customer / case I had in front of me, I say so in the report. Better than the client finding out the hard way.
  • Make the un-fun parts repeatable. Deploy scripts, smoke tests, rollback paths, idempotency guards. Everything that bit me once gets a guard rail.
