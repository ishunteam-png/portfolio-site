Jalaram Hospital

AI hospital management system, four portals

An AI-assisted hospital management system for a women’s health clinic in India. Four portals (Patient, Doctor, Staff, Admin), a tool-calling clinical AI Copilot, daily GPT-4o insights for doctors, and a data model shaped around Gynaecology and Obstetrics. Live in production. Full-stack engineer, freelance, 2025–2026.

WHAT I BUILT

Four portals, one backend. PatientPortal — the patient’s view: appointments, medical records, prescriptions, lab reports, menstrual-cycle tracker. DoctorDashboard — today’s roster, full consultation form (vitals, GPAL counts, pregnancy module, pelvic exam notes, advice), prescription builder + per-doctor templates, AI insights, Copilot chat. StaffDashboard / Ops Center — the front desk: live counts of scheduled / completed / missed appointments, pending and overdue follow-ups, reports filed today, call attempts logged with notes. AdminDashboard — users, audit log, system-wide metrics.

JALARAM SUPER-AI Copilot. GPT-4o with tool calling against the Postgres schema. Two tools: search_patients (by name or by PAT-1-2026-format hospital ID) and get_patient_context (the full clinical bundle for a given patient). The system prompt locks the assistant’s identity, names it explicitly, and says authorisation is handled at the login layer — the model is told not to refuse for “privacy” reasons inside the app, because the JWT has already done the role check. Each doctor’s chats live in CopilotSession with auto-titled threads and message history in CopilotMessage.

Doctor AI Insights. Every morning the doctor opens the dashboard and the backend runs a roster anonymisation pass: counts of today’s appointments by status, follow-up queue size, overdue follow-ups, irregular-cycle alerts (cycle length below 21 days or above 35). All PII stripped — only patient IDs make it into the prompt. GPT-4o is asked for exactly three actionable bullets in a strict, HIPAA-flavoured clinical tone, returned as HTML <li> elements so the front-end renders them directly.

“The system prompt locks the assistant’s identity and says authorisation is handled at the login layer — the JWT has already done the role check.”

Gynae / Obstetrics-shaped data model. Custom Prisma schema: PatientProfile with hospital ID format PAT-<seq>-<year>, GPAL counts (gravida, para, abortions, living children), isPregnant, EDD and pregnancy notes; MenstrualCycleLog with start/end dates, flow intensity, symptoms, cycle length, period duration, predicted next-period / ovulation / fertile-window dates; ClinicalConsultation with vitals (BP, pulse, weight, temperature), LMP and flow + pain levels, chief complaint, obstetrics history, contraceptive method, trimester + risk category, general and pelvic examination, suggested reports and advice; OperationRecord with surgeon, assistant, anaesthesia type and complications. There’s also a SystemLog table that every controller writes to via a recordLog() helper, capturing the actor, action, details and IP. That’s the audit trail the admin sees.

Reports + lab uploads. Multer-S3 to AWS S3 in the ap-south-1 region, signed URLs back to the front-end. The Report table has an aiSummary field — the next iteration auto-summarises uploaded ultrasounds and lab reports back into the patient’s timeline. Lazy-init OpenAI / S3 clients so the env is read at call time and a misconfigured deploy fails loudly instead of silently using a stale key.

Production hardening. Express 5 + TypeScript + Prisma 6 + Postgres. JWT in HTTP-only cookies, bcrypt password hashing, helmet for security headers, a CORS whitelist that includes shreejalaramhospital.live and localhost for development. 20 MB JSON body limit so report uploads with embedded base64 thumbnails still parse. Request logger middleware on every route. Two date helpers because dashboards compute “today” in IST: getTodayBounds() and getTomorrowBounds() round-trip through the +5h 30 offset rather than trusting Date defaults.

Deploy. Docker + docker-compose + Nginx (TLS) + PM2 on EC2, with Prisma migrations baked into the start script. deploy_to_live.ps1 on the local side, setup_ec2.sh + start_pm2.sh on the box. Frontend served via a small serve_frontend.cjs bridge for Vite’s built output.

THE BITS THAT BIT ME

Role logic in the controllers is the easy thing to get wrong. When a STAFF or ADMIN creates a medical record or prescription on behalf of a doctor, the supervising doctorId has to come from the request body, not the caller’s JWT. DOCTOR-role creates pull from JWT. Wrapped that branch in the controller and added a 400 if STAFF/ADMIN forgets to send the doctor’s ID — saved me a class of “prescription signed by reception” bugs.

Cycle-irregularity alerts are noisy by default — 21/35-day thresholds are textbook but pull in too many patients on a real roster. The dashboard currently flags them but I’ve been tempted to add a per-doctor configurable band; haven’t shipped that yet because the doctors actually want to see the long tail.

The OpenAI calls were originally constructed at module load. If process.env.OPENAI_API_KEY wasn’t set yet (e.g. PM2 starting before .env was fully sourced), the client was permanently broken until restart. Moved both OpenAI and S3 clients to lazy getters — getOpenAI() / getS3Client() — that re-read env at call time. Fixed by inspection, never had to debug it under load.
